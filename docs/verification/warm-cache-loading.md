# 后续启动重复构建：缓存校验合同

## 问题与修复

首次构建允许耗时；相同游戏资源、编译器及语言组合的后续启动必须复用磁盘缓存。
本次以 0.3.15 为基线，修复不包含在该版本标签中。

`MenuTranslator` 同时输出保留原始格式的 `pairs` 和去格式后的 `plain_pairs`。
完整简中／日文模型有两条纯颜色控制记录，`plain_pairs` 的 `<C4>`、`<C2>` 对应
`["", ""]`。这些是合法的规范化结果，不是缺失译文。

旧 `read_model()` 要求两个字典的每个字符串都非空，把合法缓存整体判为损坏。
随后 `ready_model()` 重新加载目录并编译，下一次读取同样拒绝刚生成的文件。
直接执行 0.3.15 的读取器验证同一份完整模型，返回 `None`；最小回归用正式编译器
生成仅含颜色控制和普通对白的模型，同样在磁盘往返时失败。

修复只调整读取合同：原始 `pairs` 仍要求两侧非空；规范化 `plain_pairs` 允许空字符串。
字典、配对数量、字符串类型和截断 JSON 的校验保留。没有删减、重新分配文本，
也没有改变资源／编译器／语言组合的缓存失效规则。已有合法缓存可直接复用。

## 检查

- 最小编译器往返回归：修改前失败，修改后完整模型字段相等。
- 三个独立 Python 进程读取同一份编译器输出；调用资源加载即失败，三次均未调用，
  模型文件修改时间保持不变。
- 缺少字段、配对数量错误、非字符串、原始译文为空、截断文件继续拒绝；原有损坏缓存重建测试通过。
- 真实完整缓存的三个独立进程：读取分别为 1.306、1.305、1.306 秒。
  各自另调用正式准备工作器约 1.53—1.55 秒，确认同一路径、没有资源编译，
  模型 204,339 个原始配对及整个文件的 SHA-256、修改时间不变。
- `tests/check_cached_connection.py` 使用正式解码器、文本／脚本／表身份／段落解析器，
  仅连接每轮自建的隐藏宿主。三轮模型读取、EXE 校验、宿主连接及索引初始化合计
  5.253、5.198、5.137 秒，其中传入及运行时初始化约 3.47—3.53 秒。

这些是本机 239,507,427 字节模型和 106,768,488 字节传输缓存的基准，
不包含真实游戏自身启动、语言表就绪及画面显示等待，不能外推为其他电脑的启动时间。
初次空缓存构建没有在本次重新计时。

证据：`generated/diagnostic-141-cache-reject.log`、
`generated/diagnostic-141-fresh-processes.json`、
`generated/diagnostic-141-cached-after.log`、`generated/diagnostic-141-check.log`。
