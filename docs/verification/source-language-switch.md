# 游戏来源语言热切换

## 问题与验收范围

2026-10-04 用户报告：游戏本身保持中文时，切换 MOD 主副语言正常；在同一游戏进程内把游戏文字改成日文／英文后，食谱等界面的映射大面积消失。用户明确补充只测试过运行中切换，不能据此声称非中文冷启动也失效。

本轮要求：

- 运行中改变游戏文字语言后，按实际来源重建索引，覆盖八种支持语言。
- 主副语言仍由用户控制；仅新游戏进程首次检测时同步主语言。
- 连续切换时旧构建结果不能覆盖新来源或最新主副语言；单语、双语、禁用状态均保持用户选择。
- 检测不能新增游戏线程钩子、逐帧全表扫描或阻塞输入轮询；工具退出须结束检测线程并关闭句柄。
- 保持已验收排版。仅交付本地 DEV，新候选经用户实机验收后才可公开发布。

## 根因与修正

`native_probe.run` 只在连接开始调用 `detect_current_language`，之后把每次配置读取的 `game_language` 强制设回最初检测值。“只在启动时同步主语言”的规则被错误延伸为“来源语言整个会话不变”。模型缓存本身已有来源语言键，词典缺少日文／英文并非这次已确认根因。

新增工具侧只读线程，每秒读取已验证 TextTableData 的四个采样键；沿用三键一致、已识别语言冲突拒绝的分类规则。首次定位扫描有界索引，后续只读取四行；表头或记录变化使指针缓存失效。检测使用 Windows 只读进程 API，不新增 Frida 会话、拦截器或游戏内调用。

来源变化沿用既有 `ModelPreparation` 异步构建与原子载入。等待可靠来源或新模型期间暂时恢复游戏原文，状态显示准备中；重新匹配后恢复用户原模式。更改来源不调用 `apply_startup_language`，不写回用户主副语言。

## 证据及边界

- 修改前：`python -X utf8 -m unittest tests.test_runtime_source_switch -v` 在真实后端循环的同 PID 中文→日文场景失败：构建记录仅为 `['zh-Hans']`，期望 `['zh-Hans', 'ja']`。OS／游戏边界及编译器为替身，循环和异步模型切换为生产代码。
- 修改后：同一入口通过；扩展覆盖八语冷启动、连续切换、禁用／单语／双语、短暂表不可读、重新启用、构建失败重试、来源及主副语言同时变化时丢弃旧结果。
- `test_runtime_source_reader.py` 使用已验证布局的原始内存字节，覆盖原地换值、表指针变化、同地址重排、读取途中重载、三键容错和异常边界；`test_process_memory.py` 只读取测试自身进程的真实内存。
- `test_native_agent.js` 通过生产 agent API 回放中文→日文→英文→中文来源，验证存活控件更新、主副单语及禁用恢复。不是游戏画面验收。
- 当前游戏 PID 43592 的外部只读采样识别为简体中文。首次含资源加载约 40 ms，随后两次为 0.567／0.366 ms；该测量属于工具侧采样，不是游戏帧率或全部电脑性能承诺。
- 完整资源回放：`python -X utf8 tests/check_source_language_models.py --game-dir <game>` 构建／加载八种来源的完整模型，逐一核对截图中的食谱、食材、持有数和烹饪按钮，192 项通过。主副输出固定日／中，比较资源原始目标值；有歧义的表文本通过生产 `TableIdentities` 身份模型检查，未声称离线验证能证明实机传入了该身份。
- 最终 `tools.dev check`：559 项 Python（5 项原有条件跳过）、174 项 JavaScript 全通过；20 项隐藏原生检查完成，其中六项需要 EXE 的检查追加 `SORA_GAME_EXE` 后实际执行通过。所有原生检查只操作自建宿主。
- Standards 审查发现“权限读取失败被误标为初始化等待”，已修正：异常保留到检测结果、日志和界面，自动重试；临时暂停翻译不再显示为用户主动停用。Spec 审查无阻塞项，Standards 复核确认已解决。
- 用户已实测 DEV1 的日文／英文来源：绝大多数界面正常，随后报告旧存档摘要和 `Hide UI` 两处遗漏；不能将此记录为后续修补候选的验收。正式版保持 0.4.1。

## 本地候选加载

本轮只更改工具侧 Python 检测与状态提示；游戏内脚本及 `POINTS` 不变。替换前核对当前 PID 创建时间及 `native-agent.json` 的驻留 revision，与磁盘生产启动源计算结果一致，再正常退出 DEV 工具、更新候选并重启，通过原有受认证控制通道接回同一 agent。此路径不重装／卸载钩子，不要求关闭当前游戏。若 revision 不一致则保留游戏，改等正常退出后加载候选。

## DEV1 验收后的存档摘要与资源键修补

存档中的章节、地点、目标和队员名是保存时的文字；当前来源语言变化后，这些旧文字仍会出现在列表、详情和确认框。普通菜单按当前源语言查询是正确的，但不能用这一个来源解释保存的数据。

`MenuTranslator.scoped.save_summary` 仅从 ChapterParam、地点、名称、NaviText 和保存详情资源编译八语别名，保留同文异译及缺失目标的冲突。只在实际存档控件使用独立解析器，不进入全局词典，不写入存档，不更改排版。读档确认长串必须同时匹配布局 8 的正文路径及完整 `TXT_TITLE_CONTINUE_CONFIRM` 前缀，其他弹窗不进入此域。

现场 `ReadProcessMemory` 采集（PID 43592）确认以下路径：

| 布局 | 控件 |
| --- | --- |
| 3 | `root/detail_info/DetailText`、`DetailText2`、`DetailText3` |
| 4 | `root/Null/texts/TitleText`、`SubTitleText` |
| 5 | `root/save_info/texts/TitleText`、`SubTitleText` |
| 8 | `root/text`，须含完整继续游戏确认前缀 |

布局 4 中同时采集到中文旧摘要与英文新摘要；布局 3/5 的控件路径存在，但当时选中空档位，正文为空。布局 8 使用前轮真实确认框采集。原始 `layout.pac` 中 `TitleText/SubTitleText` 仅存在于 `savemenu_item/yesno`，`DetailText[2,3]` 仅存在于 `savemenu_base`。测试覆盖控件复用、布局身份变更和非存档同文，不以资源字符串出现替代控件归属。

`Hide UI` 的现场布局为 88、`root/ui_hide/text`，文本键 hash `536578224`；只读运行态表确认为 `TXT_KEY_HELP_HIDE_UI`。其他界面有相同英文但不同日文，无法靠全局同句匹配。旧代码将控件原串与启动时缓存的中文比较，故切换到英文后丢失文本键。现在按当前模型中该键的完整源串验证；复用控件的残留 hash 仍不能覆盖不同原串。修复作用于全部 TXT 键，不添加这句话的特例。

回归：

- `test_native_agent.js` 直接执行生产 agent，修复前分别出现 `Hide UI` 不翻译和旧中文存档不翻译，修复后通过。覆盖中→英→日→中键切换、双语／两种单语／禁用及无关控件。
- `test_save_localization.py` 覆盖跨语保存字段、同文冲突、缺失译文、未知名称、日期及非存档对白隔离。
- `tests/check_saved_source_languages.py --game-dir <game>` 使用完整目录、日文／英文两个当前来源及八语旧存档字段；388 项核对目标原文、最终副文、混合语言确认摘要、等级与时间，以及六个同组快捷键资源。
- 双轴审查发现旧名称权威规则会用当前来源解除八语旧存档的冲突。现已禁止来源别名借用这条捷径；普通名称权威保持原行为。真实 `Elk`、`Tourist`、`Bobcat`、`菲` 及人工跨语同名反例均保持歧义原文，不能任取其中一个身份。
- 两位审查者已复核冲突修正，无剩余阻塞。最终 562 项 Python（5 项原有条件跳过）、176 项 JavaScript 通过；`tools.dev check` 的 20 项隐藏原生检查带实际 EXE 路径完成，未附加真实游戏。
- 此轮修改了驻留 JS，下一候选必须在正常退出游戏后加载；DEV1 的同进程重连步骤不能用于它。实机画面与公开发布仍待下一候选验收。
