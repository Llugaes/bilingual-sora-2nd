# 1.0.1 启动性能回归

1.0.0 已撤出 GitHub/Gitee 稳定更新。2026-10-10 按维护者委托，在同一台电脑实际运行 0.4.5 与 1.0.1 候选：工具待机及连接游戏的 CPU、私有内存和工作集中位数均不高于 0.4.5，冷启动峰值也下降。最终提交的 CI、便携 EXE 和离线安装器检查已经通过，正式包的执行代码及运行时核对完成。

## 根因与修复范围

- 自动连接每 250 ms 调用资源 fingerprint。1.0.0 将 fingerprint 从文件元数据升级为完整内容摘要，原来的轮询因此不断读取所有脚本和表资源。本机输入为 16 个档案、741,162,143 字节。修复每 30 秒只用轻量文件信息判断是否需要预热；变更时才计算完整摘要，切换语言和发布变更仍立即检查。此提示不授权复用模型，准备与每个新游戏连接入口仍校验完整内容，包括长度、时间戳相同的资源变更。
- 动态通知目录一次保留八种语言的完整脚本指令树。此路径在 0.4.5 冷缓存中也存在；升级重建让问题更容易出现。修复保留完整解析与拒绝边界，但立即释放后续生产者不用的指令数据，并按单个脚本的完整语言集合处理。系统 helper、全部物理调用与参数顺序继续保留，不缩减文本或语言。
- 本次未修改原生驻留脚本、字体渲染、布局或翻译规则。高内存峰值能够在独立编译进程中复现，任务结束后释放；没有把这个证据称为已证明的永久内存泄漏。
- 缓存身份查询不再在界面进程中提前导入完整目录解析器与翻译编译器。编译发生时才导入；常驻界面内存随之减少。
- 游戏发现与状态检查降为每秒两次，重试和退出仍通过事件立即唤醒；输入和渲染循环保持原样。字体图集的完整校验移入现有可取消准备子进程，避免大块临时字体数据留在界面进程的分配器中。
- 界面原先注册三个系统 TTC 字体集合，却只选择第一个字体。现在找到可用字体后停止注册其余备用集合，失败时仍尝试下一个。本机选中的 `Microsoft YaHei` 不变，中／英／日界面词库的 743 个不同字符全部通过实际字形覆盖检查；游戏内字体加载与字体资源不变。

## 离线证据

生产动态编译入口：修复前峰值工作集 7,338 MiB，修复后 796 MiB；修复后峰值私有内存 169 MiB。完整冷目录、模型及 wire 准备峰值私有内存 2,454 MiB、工作集 2,339 MiB。这些是本机资源和独立测试进程结果，不等同于工具完整进程树或游戏帧率。

467 条完整动态产物及完整审计结果逐项相等；简中主语言、日文副语言模型的全部 45 个根字段与原 1.0.0 发行模型相等。失败测试先证明指令树被保留以及 8 次空闲轮询触发 8 次全量摘要，再验证释放、轮询频率、周期复查和配置变化。另验证生产编译器逐批消费，不积累所有脚本。

`python -m tools.dev check` 已通过 793 项 Python 测试（9 项平台跳过）、211 项 Node 测试及全部隐藏原生宿主检查。最后的界面字体优化另通过 59 项字体／设置／手册回归；最终发布 CI 已对提交 `ddff7a8` 通过全部 795 项 Python 测试（9 项跳过）、211 项 Node 测试及原生宿主检查。包检查覆盖无系统 Python、Unicode 路径、单实例、界面重载、中断更新恢复及已加载 DLL 时的程序更新。

## 实机验收

采用原始 0.4.5 应用包，其摘要与公开更新清单相符；全部 661 个受管文件（包括实际 runtime 字节）与其 installed-manifest 相符。1.0.1 从当前代码和同一个 runtime 构建。独立解压目录、相同显示配置，按工具进程树及游戏分别记录 CPU、私有内存、工作集和启动阶段。每次切换驻留版本均使用新游戏进程；保留用户存档与原安装源文件。

测试机为 Windows / Ryzen 7 9800X3D（16 个逻辑处理器）；游戏为 Steam build 25721473、画面版本 1.04。配置均为简中主语言、日文副语言、双语注释模式，字号比例 0.85、行距 6，性能诊断同样开启。游戏采用原有 4K 设置、同一存档、同一固定场景及自然轮换的 Tips 文本，工具界面隐藏。每个版本使用独立新游戏进程，前后 70 个存档／设置文件摘要均未变化。

| 工具进程树指标 | 0.4.5 | 1.0.1 |
|---|---:|---:|
| 冷启动峰值 CPU（整机百分比） | 26.960% | 26.533% |
| 冷启动峰值私有内存 | 8,235.9 MiB | 2,633.1 MiB |
| 冷启动峰值工作集 | 8,327.0 MiB | 2,394.3 MiB |
| 不开游戏：稳定 CPU | 0.286% | 0.194% |
| 不开游戏：私有内存中位数 | 222.0 MiB | 184.3 MiB |
| 不开游戏：工作集中位数 | 231.3 MiB | 228.4 MiB |
| 连接游戏：稳定 CPU | 0.444% | 0.414% |
| 连接游戏：私有内存中位数 | 308.8 MiB | 274.5 MiB |
| 连接游戏：工作集中位数 | 335.8 MiB | 333.9 MiB |

工具私有内存在稳定待机的约 120 秒内保持 184.27–184.37 MiB，游戏稳定窗口保持 274.45–274.71 MiB。本轮没有观察到持续增长；这些短时样本不能证明全游戏、全部语言组合或长时间运行绝无泄漏。首次准备约 183 秒，0.4.5 约 146 秒，本轮没有达到冷缓存准备速度也更快的目标。稳定 CPU、私有内存和工作集均以表中固定窗口比较，不声称任意瞬时采样点都更低。

游戏进程整体计数也记录在原始数据中：该轮 CPU 为 6.61% / 9.69%，私有内存中位数为 9,440.5 / 9,459.0 MiB（0.4.5 / 1.0.1）。它包含游戏自身渲染、资源与缓存，没有做裸游戏差额测量，也没有采集聚合 FPS，因此不以本表推导游戏整体 CPU、驻留开销或帧率都得到改善。本次游戏实际验证的是工具成功连接、正常双语显示，以及该场景下工具进程树的占用；未完成菜单／战斗全场景验收。

[完整计数器样本](p0-performance-samples.csv) · [指标与逐项判定](p0-performance-summary.json)。公开数据仅含聚合性能计数，不含存档、游戏文本或个人路径。实测完整便携包 SHA-256：`8e153c7b151508adbd7e51942e2225a58aa6bfbf3dbb672a04064bab6d3a020c`。正式包的程序源码、全部运行时及其余受管文件与实测包字节一致；三个 README 加入了本报告链接。C# 启动器的 18 个不同字节仅属于 PE 构建时间和 .NET MVID：通过 .NET 反射读取两个 MVID 并核对实际文件偏移后，仅归一化这两个元数据字段即可得到完全相同的启动器。启动器源码、执行指令和资源没有变化，CI 也实际启动了这一正式 EXE。

记录方法：使用 `tests/measure_runtime_processes.ps1` 在 PowerShell 7 中每 0.5 秒读取进程计数器，`-Root` 限定完整工具进程树，`-WithGame` 同时记录游戏。CPU 按窗口内累计处理器秒差除以实际墙钟时长及 16 个逻辑处理器计算，100% 表示整机全部逻辑处理器。稳定段要求 PID 集合不变；内存记录 Private Bytes 与 Working Set，单位 MiB。准备进程计入冷启动峰值，准备完成后观察稳定待机；游戏固定场景采样 150 秒，剔除前 30 秒后比较。

最初的临时 PowerShell 采样器误用了 `Math.Max(0, double)`，逐帧 CPU 差值被选中的整数重载取整；原始每进程累计 CPU 浮点计数未受影响。最终统计从原始计数重算，已发布的采样脚本使用 `Math.Max(0.0, [double]...)`。启动与稳定指标分别报告，不混用不同窗口的平均值。

中间候选没有算作通过：第一版的待机 CPU 略高于基准；随后一版游戏内 CPU 为 0.453%，仍高于 0.4.5 的 0.444%；再一版 CPU 和私有内存已低于基准，但游戏内工作集为 351.7 MiB，高于基准的 335.8 MiB。继续移除未选中的界面字体注册后重新打包和实测，没有通过修改基准或删除失败指标放行这些候选。
