# 地图移动顿挫：0.3.25 诊断支持，尚未确认修复

2026-09-30，基线 `da8f3e3`（0.3.24）。实际运行进程的驻留摘要与安装文件一致，不能归因于未重启或仍在使用旧补丁。用户继续观察到地图移动时偶发数百毫秒暂停。

## 已取得的证据

- 现有计时从进入 JavaScript 之后开始，不含游戏线程等待脚本锁的时间；Update 本身也没有完整计时。旧指标没有长耗时不能证明 MOD 没有阻塞。
- 完整本机语言缓存及正式解析器，在独立隐藏宿主中强制回收内存需要约 308–341 ms。这只证明风险，不证明自然游玩中的暂停由回收触发。
- 稳定 Update 回放 100 万次，最大一组 100 次调用约 6.4 ms；独立原生线程回放 20 万次，最大一组约 1.74 ms。增加临时 UTF-8 分配的独立线程回放 30 万次，最大一组约 7.2 ms。这些回放未复现用户报告的数百毫秒顿挫，不能据此宣称修复。
- 当前游戏只读取已有状态与进程内存统计，没有重新附加 Frida、安装探针或更换驻留脚本。系统性能跟踪没有启动成功，也没有停止其他人的跟踪。

## 候选增加的证据入口

配置 `performance_diagnostics: true` 只在新游戏进程安装驻留代码时读取，默认关闭。它与会输出文本快照的 `diagnostics` 独立。

`native_timing.js` 在原有 SetText / Update JavaScript listener 前后各安装一个纯原生观察 listener。原有回调对象、参数替换、返回值、线程和嵌套调用语义保留，不增加 JavaScript 回调。分别记录：

- enter：进入原有 JavaScript 回调之前到该回调结束，包含等待脚本锁的时间。
- body：原生函数区间，可能包含它调用的其他 MOD 钩子，不能直接当作纯游戏耗时。
- leave：原有退出回调的等待及执行时间。

原生端仅保留最近 32 个总耗时至少 8 ms 的调用及累计指标。使用单调时钟，导出时映射为实际时间。超过线程／嵌套容量时只增加丢失计数，不阻止原调用；不访问或持久化正文。

后端每秒原有状态读取顺带取回数据，按序号去重写入 `generated/native-performance.jsonl`。512 KiB 后轮换一次，最多保留当前文件及 `.previous.jsonl`；记录模式、进程会话、采样缺口。磁盘错误不终止游戏连接。

## 回归及边界

命令：`python -X utf8 tests/check_native_timing.py`。

独立隐藏宿主主动让一个原生线程等待脚本锁：原有回调内部计时为 0 ms，新的 enter 计时捕获约 173–178 ms。另覆盖进入／原生体／退出各自延迟、返回值替换、调用状态、6 层原生递归、32 条环形容量，以及正式 Update 冷热刷新与动画的 6 项合同。

同一宿主每 10,000 次调用的额外成本约 3–4 ms，约 0.3–0.4 微秒／次。这不是游戏帧时间。`tests/test_performance_journal.py` 检查去重、保留事件时间和模式、丢样提示、写入失败重试及容量轮换。

剩余步骤：在新进程中启用此候选，记录实际游玩顿挫的时间，区分脚本等待、回调工作及原生函数区间。尚无这层证据，故没有发布“卡顿已修复”的结论，也没有按内存回收猜测更换模型结构或过滤文本。

用户确认先按现状发布 0.3.25。本轮代码检查通过：454 项 Python（5 项跳过）、162 项 JavaScript，以及隐藏原生宿主检查。可取得 EXE 的机器码检查另外运行；游戏仍需新进程中的实际顿挫采样。
